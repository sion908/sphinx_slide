## 1. はじめに & プロジェクト背景

### 開発対象: Locker OS (v0.4.0)
- **概要**: KERONG製の業務用スマートロッカーを、現地のRaspberry Pi（Edge）とクラウドから安全に制御・管理するシステム。
- **v0.4.0のミッション**: 既存のPHP + SQLite構成から、AWS（Go Lambda + DynamoDB + IoT Core / MQTT + S3 / CloudFront + Cognito + CDK）へのフルリプレイス。
- **開発スタイル**: 完全なAIネイティブ開発（要件定義、ドメイン設計、IaC、実装、テスト、レビューまでAIを最大限活用）。

ここで白羽の矢が立ったのが、AI主導のライフサイクルフレームワーク **「AI-DLC」** でした。

---

## 2. AI-DLC（AI-Driven Development Lifecycle）への挑戦

### AI-DLCとは何だったのか？
- ソフトウェア開発ライフサイクル（SDLC）をAIエージェント群が自律的に推進する仕組み。
- **Ideation → Inception → Construction（設計・実装）** とステージを進める。
- 各ステージ間には「ゲート承認」「監査ログ（Audit Log）」「アドバイザリーレビュー」「人間ターン（HUMAN_TURN）」が厳密に定義され、品質とトレーサビリティを担保する設計。

### 18ステージを突破した設計フェーズ
- AI-DLCは見事に機能し、以下の重要成果物を一気通貫で生成：
  - 要件定義（FR / NFR 38項目）
  - ユーザーストーリー（23件）
  - ドメイン設計 & ユニット分割（U1〜U8）
  - システム境界契約（C1〜C5: Cloud-Edge間MQTTプロトコル等）
- 「これはすごい、完全にAIだけでエンタープライズ品質の設計ができる！」と手応えを感じていました。

---

## 3. 何が起きたか？（直面した現実と環境バグ）

設計が完了し、いざ実装ステージ（Construction: 3.3 NFR Design）へ進もうとしたところで、**突如としてシステムが進行不能**になりました。

### 踏んだトラブル①: サブエージェント委譲の機能不全
- AI-DLCは専門エージェント（アーキテクト、レビュー、コンポーザー等）へタスクを委譲して並行作業する設計。
- **しかし環境（ACP経由のkiro-cli）の不具合により、子エージェントにツールが継承されない**（Kiro Issue #6714, #6887）。
- 委譲されたエージェントが「ファイル読み書きすらできない丸腰」で立ち上がり、即座にタスク失敗。
- （回避策としてConductorがインラインで代替起草して凌いでいた）。

### 踏んだトラブル②: フック機構の完全凍結（hook-heartbeat-frozen）
- 監査ログを調べると、フックが100時間以上発火していない。
- 人間が承認レスポンスを返しても `HUMAN_TURN` が監査ログに記録されない。
- その結果、**「要約確認」「レビュー開始」「ゲート承認」といった人間の承認を前提とするガード条件が永久に解除されない**状態に。

### 踏んだトラブル③: 整合性エラーの地獄
- PostToolUseフックが飛ばないため、成果物が認識されず `SUMMARY_ARTIFACT_UNAUTHORIZED` や `REVIEW_EVIDENCE_MISSING` が連発。
- 手動で redo jump して write ツールで再保存して……と回避作業に何時間も溶かす事態に。

> **結論**: 設計やコードの問題ではなく、**「ワークフロー進行フレームワーク（フックや委譲）の運用不全」** で完全に足止めを食らってしまった。

---

## 4. それに対して行ったこと（AI-DLCの停止と資産凍結）

納期が迫る中、フレームワークのバグと格闘し続けるのは本末転倒でした。

### 決断（2026-09-30）
1. **AI-DLCのワークフロー進行を正式に停止**
   - ゲート承認やステージ進行、監査記録などのAI-DLC機構を完全に終了。
2. **生成物を「仕様の正本」として凍結保存**
   - AI-DLCが苦労して吐き出してくれた18ステージ分の設計成果物は極めて優秀。
   - これらを `aidlc/spaces/default/intents/...` 配下に**読み取り専用で凍結**し、開発の「仕様の正本」に据える。
3. **切替前の「縦断整合性レビュー」を実施**
   - FR/NFR → User Story → Component → Unit → Contract のトレーサビリティを総点検（38項目中37項目完全一致、1項目は正当な後段委譲）。
   - 「設計は完璧に整合している」と確証を得た上で、**「素の実装（開発者AIが直接実装するスタイル）」** へシフト！

## 5. 「Bolt」アプローチでの実装と、その落とし穴

AI-DLCを止めた後、どうやって実装を進めたのか？
そこで採用したのが、AI-DLCの設計書に含まれていた **「Bolt（ボルト）」** という考え方でした。

### Bolt とは何か？
- **定義**: システムを機能縦断で一気通貫に通す **「Walking Skeleton（歩く骨格）/ 垂直スライス」** の単位。
- 「UIだけ」「DBだけ」と横割りに作るのではなく、受取解錠なら「UI → Cloud API → MQTT → Edge → ロッカーハード制御」までを1本の稲妻（Bolt）のように縦断で貫通させる。

### 当初の Bolt 計画
- **Bolt 1**: 受取解錠の縦断スケルトン（最難関のCloud-Edge境界を最速で貫通）
- **Bolt 2**: 認証・監査基盤
- **Bolt 3**: インフラ IaC（CDK整備）
- **Bolt 4**: 予約集約・外部連携
- **Bolt 5**: 受渡タイプ拡張（返却・預入など）
- **Bolt 6**: 店舗・管理UI
- **Bolt 7**: 個人情報削除

### Bolt1〜7を完走！……しかし？
開発者AI（Kiro+agy）によってBolt 1からBolt 7まで順調に実装。
各Boltの単体テストやローカル結合テスト（moto/cu-emulator）もパスし、各Boltレビューでは **「Critical/High = 0」** を達成。

「よし、これで全機能完成だ！」と誰もが思いました。

## 6. 2026-10-02 システムレベル批判的評価の衝撃

Bolt 7まで作り終えた段階で、システム全体を通した「システムレベル批判的評価（反証スタンスでの全体レビュー）」を実施しました。

そこで明らかになったのは、**戦慄の事実**でした。

### 噴出したCritical/High欠陥（一部抜粋）
- **C1: APIに認可がない**
  - 認証ミドルウェアが一切なく、無認証で管理操作（箱状態強制変更、代行解錠、監査ログ閲覧、全タスク一覧）が通る。
- **C2: ハッシュ（CredentialRef）をPINとして入力すると解錠できる**
  - 平文フォールバック比較ロジックがあり、DB内のハッシュ値をそのまま送ると誰でもロッカーが開いてしまう。
- **C3: 通常タスクへのPIN発行処理が存在しない**
  - テストコードが直接DBにハッシュを注入していたため、本番フローで利用者にPINが届かないことに気づかなかった。
- **C4: Go Lambdaで動かない**
  - なぜか常駐HTTPサーバ（`http.ListenAndServe`）として実装されており、Lambda用のハンドラがない。CDKのデプロイ定義もダミーのまま。
- **C5: BOX状態がDynamoDBに永続化されない**
  - インメモリのまま放置されており、再起動するとロッカーの状態がすべて消える。
- **H1: 在荷（IRセンサ）情報が更新されない**
  - ハードからのセンサー結果がクラウドのDBに反映される経路がどこにも繋がっていない。

### なぜこんなことが起きたのか？（Boltの盲点）
1. **「スコープの押し付け合い」によるエアポケット**:
   - Bolt 1の実装時:「認証はBolt 2でやるからスコープ外」
   - Bolt 2の実装時:「受取APIとの結合は後段で」
   - Bolt 3の実装時:「Lambda化は後でラッパーを書けばいい」
   - ⇒ **各Boltのスコープ内では100点満点だが、BoltとBoltの狭間にある「システム横断の関心事」が丸ごと抜け落ちていた！**
2. **「前提データの直接注入」というテストの罠**:
   - 縦断テストが「あらかじめDBにハッシュや状態を直接INSERT」して動かしていたため、「入口（予約・PIN発行）から出口（解錠・永続化）」までの実データ連携の欠落に誰も気づけなかった。

## 7. 「Bolt」と「Spec」の違いとは？

この痛烈な反省から、開発の進め方を **「Bolt」から「Spec」** へ根本的に再編しました。

### 比較まとめ

| 観点 | Bolt（ボルト） | Spec（仕様・修正単位） |
| :--- | :--- | :--- |
| **位置づけ** | **機能縦断の垂直スライス** (Walking Skeleton) | **測定可能な要件・修正の契約単位** |
| **スコープの切り方** | ユーザーストーリー・機能シナリオ単位 | 境界・認可・運用・データ整合性などの関心事単位 |
| **強み** | 最初の一気通貫（骨格）を素早く通せる | 盲点・境界の欠落を許さず、全体整合性を担保できる |
| **弱み・落とし穴** | スコープ外への押し付け合いでエアポケットが生まれる | 最初から細かく切りすぎると全体像が見えにくくなる |
| **実例** | Bolt 1: 受取解錠スケルトン<br>Bolt 2: 認証・監査基盤 | spec-A: API認可・認証バイパス修正<br>spec-B: 資格発行・永続化・実データ化<br>spec-C: Go Lambda・IaC・MQTT化<br>spec-ENT1: 組織・設備モデル（ENT1a〜dへ分割） |

### Spec運用の新ルール
1. **3点セットの義務化**: `.design/specs/<slug>/` 配下に `requirements.md`（測定可能な基準）、`design.md`（前提とアーキ）、`tasks.md`（作業分解）を作成。
2. **実装前レビューの必須化**: コードを書く前に、反証スタンス（壊れている証拠を探す）でSpecの事前レビューを通す。
3. **大きすぎるSpecの分割**: レイヤーを跨ぐ巨大なSpecは、実装前にサブSpec（例: ENT1a, ENT1b...）に小さく分割する。
4. **テストの前提データ直接投入の禁止**: 入口から出口まで実リクエストと実DB永続化を通す。

## 8. 現在たどり着いた開発プラクティス

AI-DLCの挫折、Boltの落とし穴を経て、現在は極めて安定した開発フローが確立しています。

```
人間（あなた）
   │
   ▼
Kiro (Claude) ───【オーケストレータ】
   ├─ Spec作成・要件定義
   ├─ 実装前の批判的レビュー（反証スタンス）
   ├─ agy への実装委譲 ───────────────┐
   │                                   ▼
   │                             agy (Gemini) ───【実装担当】
   │                                ├─ 高速・安価なコード実装
   │                                ├─ 単体テスト作成
   │                                └─ 第1層：自己批判（自己修正）
   │                                   │
   ▼                                   │
Kiro による第2層：批判の監査 ◀─────────┘
   ├─ 異モデル（Cross-Family）視点で盲点を捕捉
   └─ 合格判定 → マージ（NGなら差し戻し）
```

### なぜこの形が強いのか？
- **トークンコストの最適化**: 思考力の高いClaudeに計画・監査を任せ、コーディングと反復試行は高速でコストパフォーマンスの高いGemini（agy）に任せる。
- **Cross-Family（異モデル）批判的評価**:
  - 同一モデルだと「自分が書いたバグ」を自己レビューで見落とす（例: Go版数の不整合やビルド制約）。
  - 別ファミリのモデルが反証スタンスでツッコミを入れることで、致命的な見落としを確実に捕捉できる。

## 9. まとめ & 学び

### 今回の挑戦から得られた教訓

1. **フレームワークに固執せず、生成物を救出せよ**
   - AI-DLCの進行フックが壊れた時、ツールのデバッグに固執せず「設計成果物を凍結して素の実装へ逃げる」判断をしたことでプロジェクトが救われた。AIが作った「良い設計ドキュメント」は人間・AI問わず最高の財産になる。
2. **「機能が通った（Bolt）」と「システムが動く（Spec）」は別物**
   - 垂直スライスは初期開発には有効だが、セキュリティや非機能要件、システム横断の関心事は必ずエアポケットに落ちる。
   - 全体結合時の「敵対的・批判的レビュー」なしに本番には行けない。
3. **AI開発は「モデルの分業」と「批判（Critique）」で完成する**
   - 「1つのプロンプトで全部作らせる」のは幻想。
   - 計画（Claude）× 実装（Gemini）の分業、そして「褒めるレビュー」ではなく「壊れている証拠を探す批判的評価」の二重構造こそが、高品質なコードを生み出す鍵。
